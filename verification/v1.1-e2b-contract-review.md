## Contract: `cmc_dex_token`

1. **Tool name:** `cmc_dex_token`.
   **Description (frozen wording):** "Get CoinMarketCap DEX token detail (metadata, market, liquidity and pool fields) for one token identified by platform name and token contract address; use platform-list to discover platform names." House style (leading capital, terminal period) as for the other 20 descriptions.
2. **Route:** `GET /v1/dex/token` on the fixed keyless base `https://pro-api.coinmarketcap.com/public-api`; one tool ↔ one allowlisted route; no credentials, auth headers or authenticated fallback.
3. **Input schema:** strict object, `additionalProperties: false`, required `platform` and `address`, no optional fields, no defaults.
4. **Types:** reuses E2-A's `DexPlatform` (1–64 chars; no control characters, `&`, `=`, `?`, `#`, or leading/trailing whitespace; case preserved; no local enum) and `DexAddress` (`^[A-Za-z0-9_.:-]{1,128}$`; case preserved; no chain-specific `0x`/length rule) **unchanged**. The JSON-schema fragments for both properties must be identical to `cmc_dex_token_price`'s.
5. **Query serialization:** exactly `{"platform": <platform>, "address": <address>}` — those provider keys, that order, values passed through unchanged (no case folding, trimming or checksum normalization). Built by a new top-level pure helper `models.dex_token_params(platform, address)` so the query construction is visible to mutmut; the handler only delegates to it. (Calling `dex_token_price_params` from D3 is not allowed: it would couple two routes' wire contracts and leave D3's call site without attributable mutants.)
6. **Omitted provider parameters:** none are documented beyond `platform`/`address`. The secondary `network_slug` / `contract_address` / `platform_crypto_id` names are not exposed. No `convert`, `aux`, paging or size parameter.
7. **Cache TTL: 15 seconds.** `TokenDetailDTO` mixes static metadata with fast-moving price, 24h high/low, liquidity, market-cap and period stats that are the same class of data D4 caches for 15 s. Using D4's TTL keeps two views of the same token from drifting by more than one short window; a longer metadata-oriented TTL (e.g. 300–900 s) would serve stale prices. Success-only caching per the existing client; failures are never cached. Caching is not a correctness dependency.
8. **Output:** the existing `ProviderEnvelope` passthrough; `data` (the `TokenDetailDTO` object, including nested `pls`, `sts`, `cexs`, `sig`) preserved verbatim; no field renaming, numeric/string coercion, filtering or derived values. String-typed market values stay strings.
9. **Errors and bounds:** the existing stable `ErrorCode` taxonomy (`errors.py`), unchanged:
   - validation failure → `INVALID_ARGUMENT`, before any network access;
   - timeout → `UPSTREAM_TIMEOUT`; network error → `UPSTREAM_NETWORK_ERROR`;
   - HTTP 429 after bounded retries → `RATE_LIMITED`;
   - retryable 5xx after bounded retries → `UPSTREAM_5XX`;
   - HTTP 400 and other non-429 4xx → `UPSTREAM_HTTP_ERROR`, not retried;
   - non-success `status.error_code` → `UPSTREAM_APPLICATION_ERROR`;
   - malformed or structurally unexpected 2xx, and any response above the shared **2 MiB** cap (`DEFAULT_MAX_RESPONSE_BYTES`, raised by `client._raise_oversized`) → `UPSTREAM_CONTRACT_MISMATCH`.
   `UNSUPPORTED_ROUTE` and `INTERNAL_ERROR` are never produced for D3 by classification. D3 has no provider paging; `pls` is bounded by the provider's top-pool count (`nps`) and by the 2 MiB cap. An unknown token yields whatever the provider returns under the mapping above.
10. **Minimum verifier shape (documentation-derived):** `data` is a non-empty mapping whose `addr` is a non-empty string. Rationale:
    - `addr` is the identity the caller supplied and the one field whose presence follows from a successful lookup; it is a string in the DTO.
    - `addr` is **not** required to equal the requested address: case (EVM checksum vs lowercase) may legitimately differ and was not live-verified.
    - `n` and `sym` are not required: names/symbols for newly created or obscure tokens may be empty, and they add no identity proof beyond `addr`.
    - `plt` is not required: the DTO marks nothing required, and E2-A showed platform naming varies in case (`Ethereum`/`ethereum`), so neither presence nor equality is stable enough to gate on without live evidence.
    - No market field (`p`, `mcap`, `liqUsd`, …) or nested list is required; their types (string vs number) are inconsistent across DEX DTOs and examples are not contracts.
    The check reuses the existing `verify_live._is_nonempty_str` helper (non-empty `str`; whitespace-only is not specially rejected, matching the D11 `n` check).
    Deterministic live fixture (for the pending live run): Ethereum USDC, `platform="Ethereum"`, `address="0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48"`, the same fixture as D4. If live evidence later shows `addr` absent or non-string, record a contract mismatch and amend this record; do not loosen silently.

## Required non-live tests

- Existing 20 tools (13 v1 + 5 E1-R + 2 E2-A) unchanged: names, descriptions, schemas, routes, TTLs.
- `cmc_dex_token` name, description, route, 15 s TTL pinned; total tool count 21; route allowlist contains `/v1/dex/token` exactly once.
- Schema snapshot: strict, required `platform`/`address`, no other properties; property fragments equal to `cmc_dex_token_price`'s.
- Validation before network (zero upstream calls): missing either field; unknown field; empty; overlong (65-char platform, 129-char address); leading/trailing whitespace; control characters; `&`, `=`, `?`, `#` in platform; `/`, space, `%`, `&` in address; non-string types.
- Boundary acceptance: 64-char platform, 128-char address, inner spaces/parentheses/non-ASCII platform name (e.g. `B² Network`), mixed-case address.
- `dex_token_params`: exact keys, key order, value identity, no extra keys; handler delegates to it (wire-level test of the actual query string, including case preservation and percent-encoding of inner spaces).
- Request is GET to `https://pro-api.coinmarketcap.com/public-api/v1/dex/token`; no auth/API-key header.
- `ProviderEnvelope` passthrough with a realistic `TokenDetailDTO` fixture (string market values and nested `pls`/`sts` preserved byte-for-byte after JSON round-trip).
- Error mapping asserting exact codes: timeout → `UPSTREAM_TIMEOUT`; network error → `UPSTREAM_NETWORK_ERROR`; HTTP 429 → `RATE_LIMITED`; retryable 5xx → `UPSTREAM_5XX`; HTTP 400 → `UPSTREAM_HTTP_ERROR` (single attempt); provider application error → `UPSTREAM_APPLICATION_ERROR`; malformed envelope and over-2 MiB response → `UPSTREAM_CONTRACT_MISMATCH`.
- Caching: success hit within 15 s; failures not cached; distinct `(platform, address)` keys not conflated, including case-only differences (`Ethereum` vs `ethereum`, mixed- vs lower-case address); D3 and D4 caches independent for the same identity.
- Verifier: accepts mapping with non-empty string `addr`; rejects non-mapping, empty mapping, missing `addr`, empty `addr`, non-string `addr`; does not require `n`, `sym`, `plt`, `p`; probe list contains exactly one D3 probe with the Ethereum USDC fixture.
- D5, D6, D12, D15, D17 and every other unapproved DEX route absent.

## Limitations

- Verifier shape is documentation-derived; no live D3 response has been observed in E2-B. Live D3 verification is pending.
- Platform-name semantics for D3 are inferred from D4's live evidence (Ethereum only) and identical documentation; `ETH`/numeric platform forms, non-EVM addresses and case sensitivity remain unverified, as in E2-A.
- Whether D3 echoes `addr` in requested or canonical case is unknown; the verifier deliberately does not compare it.
- `pls` size is not documented beyond `nps`; boundedness relies on the shared 2 MiB cap.
- Documentation was read through a fetch service because the sandbox egress blocks `coinmarketcap.com`.
- `verification/v1.1-route-recon.md`, referenced by the E0 inventory, is not present in the repository; E2-B relies on the inventory row and current documentation instead.
- This record does not accept any implementation and does not satisfy any part of the 32/32 live release gate.
