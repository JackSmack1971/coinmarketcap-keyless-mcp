## Contract: `cmc_dex_platform_detail`

1. **Tool name:** `cmc_dex_platform_detail`.
   **Description (frozen wording):** "Get CoinMarketCap DEX detail for one blockchain platform identified by platform name; use platform-list to discover platform names." Leading capital and terminal period, as for the other 21 descriptions.
2. **Route:** `GET /v1/dex/platform/detail` on the fixed keyless base `https://pro-api.coinmarketcap.com/public-api`; one tool ↔ one allowlisted route; no credentials, auth headers or authenticated fallback.
3. **Input schema:** strict object, `additionalProperties: false`, exactly one property, `platform`, **required**, no default. The provider marks `platformName` optional, but the behavior without it (a default platform, an error, or something else) is undocumented and unverified. A tool whose single purpose is "detail for one platform" therefore requires the identity. This is a deliberate narrowing, per AGENTS.md: "preserve the narrower safe behavior".
4. **Public argument name: `platform`** (not `platform_name`). Rationale:
   - The value is the same platform name, with the same type, as the `platform` argument of `cmc_dex_token_price` and `cmc_dex_token`. One name for one concept lets a caller pass the same value across all DEX tools without a per-tool translation.
   - The repository has no `*_name` argument elsewhere, so `platform_name` would introduce a second spelling for an identical concept.
   - The public→provider mapping is explicit and pinned: public `platform` → provider query key **`platformName`** (exact camelCase spelling). The tool never sends a `platform` key to this route.
5. **Type:** reuses E2-A's `DexPlatform` **unchanged**: 1–64 characters; no control characters, `&`, `=`, `?` or `#`; no leading or trailing whitespace; case preserved; no local enum or normalization. The JSON-schema fragment for `platform` must be identical to the `platform` fragment of `cmc_dex_token_price` and `cmc_dex_token`. No platform identity semantics beyond D4's live evidence are assumed; numeric IDs (`1`), acronyms (`ETH`) and other forms are passed through if they satisfy `DexPlatform`, and whatever the provider returns for them is classified by item 9.
6. **Query serialization:** exactly `{"platformName": <platform>}`. That is the only key, the value is passed through unchanged (no case folding, trimming or mapping to IDs), and no other key is sent. It is built by a new top-level pure helper `models.dex_platform_detail_params(platform)`, so the key spelling is visible to mutmut; the handler only delegates to it. Reusing `dex_token_params` / `dex_token_price_params` or building the dict inline in the nested handler is not allowed.
7. **Omitted provider parameters:** none others are documented. No `id`, `platform`, `pltA`, `convert`, `aux`, paging or size parameter.
8. **Cache TTL: 900 seconds.** `PlatformDTO` is slow-changing platform metadata (name, IDs, explorer URL formats, display flags, DEX count). It is the same DTO and data class D11 caches for 900 s, so the same TTL keeps the list and detail views consistent within one window. D12 carries no fast-moving market data, so a 15 s TTL would only add upstream load. Caching is success-only per the existing client; failures are never cached. Caching is not a correctness dependency.
9. **Output:** the existing `ProviderEnvelope` passthrough. `data` (the `PlatformDTO` object) is preserved verbatim: no renaming, coercion (for example `dn` stays a string), filtering or derived fields.
10. **Errors and bounds:** the existing stable `ErrorCode` taxonomy (`errors.py`), unchanged:
    - validation failure (missing, unknown, empty, overlong, forbidden character, edge whitespace, non-string) → `INVALID_ARGUMENT`, before any network access;
    - timeout → `UPSTREAM_TIMEOUT` and network error → `UPSTREAM_NETWORK_ERROR`, each after 3 attempts (`DEFAULT_MAX_ATTEMPTS`);
    - HTTP 429 → `RATE_LIMITED` after 3 attempts;
    - HTTP 502/503/504 → `UPSTREAM_5XX` after 3 attempts; HTTP 500 → `UPSTREAM_5XX` on a single attempt;
    - HTTP 400, 404 and other non-429 4xx → `UPSTREAM_HTTP_ERROR`, single attempt;
    - non-success `status.error_code` → `UPSTREAM_APPLICATION_ERROR`;
    - malformed or structurally unexpected 2xx, and any response above the shared **2 MiB** cap (`DEFAULT_MAX_RESPONSE_BYTES`, via `client._raise_oversized`) → `UPSTREAM_CONTRACT_MISMATCH`.
    `UNSUPPORTED_ROUTE` and `INTERNAL_ERROR` are never produced for D12 by classification. An unknown platform name produces whatever the provider returns, classified by this mapping; it is never reinterpreted.
11. **Minimum verifier shape (documentation/D11-derived):** `data` is a mapping whose `id` satisfies the existing `verify_live._is_positive_int` (a positive non-bool `int`) and whose `n` satisfies `_is_nonempty_str`. Rationale:
    - This is D11's accepted per-item identity evidence applied to the single-object DTO. It is narrowed from "integer" to "positive integer" because every live D11 identity seen (Ethereum `id=1`) and the documented example are positive, and an ID ≤ 0 would not identify a platform.
    - `n` is **not** compared with the requested name, because case may differ (E2-A showed `Ethereum`/`ethereum` both accepted).
    - `pltA`, `chId`, `cid`, `wcId`, URL formats, flags and `dn` are not required: they are optional in the DTO and add no identity proof.
    - **Deterministic live fixture:** `{"platform": "Ethereum"}`, the platform name observed live in E2-A. *(Clarified at acceptance, 2026-10-02: this is the public tool-argument fixture. `verify_live.LiveProbe.params` are provider query parameters passed straight to `client.get`, so the live probe stores `{"platformName": "Ethereum"}`, which is `dex_platform_detail_params("Ethereum")` under item 6.)* If live evidence later shows `id`/`n` absent or mistyped, or a list instead of an object, record a contract mismatch and amend this record; do not loosen silently.

### Live-fixture representation judgement

**Documentation ambiguity; the implementation is correct.** `LiveProbe.params` are not MCP arguments: `verify_live` passes them straight to `client.get(probe.route, params)`. A probe storing `{"platform": "Ethereum"}` would send the query key `platform`. That violates item 5 ("The tool never sends a `platform` key to this route") and item 6 ("exactly `{"platformName": <platform>}`"). So a literal reading of item 11's fixture as the `LiveProbe.params` shape contradicts the frozen serialization clauses. The only reading consistent with the whole contract is the semantic one: tool input `platform="Ethereum"`. The implementation stores `{"platformName": "Ethereum"}`, and a test pins it to equal `dex_platform_detail_params("Ethereum")`. Items 11 and "Required non-live tests" are annotated above. This is a clarification only and does not change contract semantics.
