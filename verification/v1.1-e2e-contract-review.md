1. **Token category reference** — <https://coinmarketcap.com/api/documentation/pro-api-reference/token>, section "Get security detail" (listed as `/v1/dex/security/detail - Get Security Detail`):
   - "Get security audit information for a token";
   - "Available with no API key … Prefix the path with `/public-api`: `https://pro-api.coinmarketcap.com/public-api/v1/dex/security/detail`";
   - the cURL example is a plain request with no `-X`, no request body and no JSON content type (sibling sections that are POST, e.g. trending tokens, are labelled POST and document a request body); with the keyless page's GET-only rule this fixes the method as GET;
   - query parameters: exactly `platformName` ("Platform name") and `address` (no description rendered); no other parameter; no required markers visible in the retrieved rendering;
   - response 200 "Token security response", rendered as a **JSON array** of `TokenSecurityResponseDTO` (`[ { … } ]`). Documented fields: `platformName` (string), `platformId` (int32), `tokenContractAddress` (string), `securityLevel`, `categoryLevel`, `securityBatchLevel` (int32), `extra` (`BnSecurityExtraInfoDTO`: example keys `buyTax`, `sellTax`, `isFlaggedByVendor`, `isVerified`, `isReported`, `source`), `securityItems` (`SecurityItem[]`: `code`, `riskCode`, `riskyLevel`, `isHit`, `order`, `des`, `groupId`), `evmDisplay` / `solanaDisplay` (display objects whose values are status strings), `exist` ("token security exist"), and `tags` (string array). No field is marked required. The example's `extra.source` is `"GoPlus"`, i.e. third-party vendor data.
2. **Schema reference** — <https://coinmarketcap.com/api/documentation/pro-api-reference/~schemas>, `TokenSecurityResponseDTO`: same fields; no required markers.
3. **Keyless Public API reference** — <https://coinmarketcap.com/api/documentation/pro-api-reference/keyless-public-api>: "18 Standard API and 17 DEX endpoints, keyless"; the DEX table lists `/v1/dex/security/detail` "Get security detail"; "Keyless endpoints accept `GET` only and return the exact same JSON envelope … as the keyed Pro API"; no `X-CMC_PRO_API_KEY` needed. The array arriving as `data` in the `{status, data}` envelope follows from this statement, not from a D8-specific envelope example.

### Evidence on empty or incomplete results

No reference page states what is returned for a token with no security record. Supporting (non-normative) evidence:

- the DTO carries `exist` ("token security exist"), so the provider models absence of a security record explicitly; nothing is marked required, so `securityItems`, `extra`, display objects, `securityLevel` and `tags` may be absent;
- the response is an array, not a single object, so zero elements is structurally expressible;
- CoinMarketCap's own Academy tutorial for this route (coinmarketcap.com/academy, "How to Build a Moonshot Memecoin Tracker with CoinMarketCap API", 2026-06) handles `data` as a list with `results[0] if results else {}`, and states that for very new tokens the vendor audit may not yet be processed and `securityItems` "will be empty or absent". This is tutorial material, not the API reference, and is used only to avoid over-constraining the verifier.

Conclusion: an empty `data` array and an element without security findings are both treated as legitimate successful responses, not `UPSTREAM_CONTRACT_MISMATCH`.

### Reconciliation with accepted E2-A/B/C token identity

E2-A (live, 2026-10-02) established that the D4 `platform` + `address` pair accepts platform *names* (`Ethereum` and `ethereum` for Ethereum USDC) and approved the bounded, case-preserving `DexPlatform` / `DexAddress`; E2-B and E2-D reused them unchanged. D8 documents the same identities: `platformName` described as "Platform name" (the same provider key E2-C uses for D12) and `address` (the same key and meaning as D3/D4). Nothing indicates a different value domain, so:

- the public interface keeps `platform` + `address`; only the provider wire key for the platform differs (`platform` → `platformName`), exactly as E2-C;
- numeric platform ids are not exposed (`DexPlatform` accepts digit strings, but numeric-id semantics are unverified and not a contract).

## Contract: `cmc_dex_security_detail`

1. **Tool name:** `cmc_dex_security_detail`.
   **Description (frozen wording):** "Get CoinMarketCap DEX token security audit records for one token identified by platform name and token contract address; returns provider and third-party vendor data as-is, not a safety guarantee; use platform-list to discover platform names." House style (leading capital, terminal period).
2. **Route:** `GET /v1/dex/security/detail` on the fixed keyless base `https://pro-api.coinmarketcap.com/public-api`; one tool ↔ one allowlisted route; no credentials, auth headers, request body or authenticated fallback.
3. **Input schema:** strict object, `additionalProperties: false`, required `platform` and `address`, no optional fields, no defaults.
4. **Public argument names:** `platform` + `address`, consistent with D3/D4/D16. No `platformName` public argument; the provider spelling is a wire detail.
5. **Types:** E2-A's `DexPlatform` (1–64 chars; no control characters, `&`, `=`, `?`, `#`, or leading/trailing whitespace; case preserved; no local enum) and `DexAddress` (`^[A-Za-z0-9_.:-]{1,128}$`; case preserved; no EVM `0x`/length rule) reused **unchanged**. The JSON-schema fragments for both properties must be identical to `cmc_dex_token`'s.
6. **Query serialization:** exactly `{"platformName": <platform>, "address": <address>}` — those provider keys, that order, values passed through unchanged (no case folding, trimming, checksum normalization, or name→id mapping). Built by a new top-level pure helper `models.dex_security_detail_params(platform, address)` so the key construction is visible to mutmut; the handler only delegates to it. Reusing `dex_token_params`, `dex_platform_detail_params` or any other helper is not allowed (wrong keys, and it would couple route wire contracts).
7. **Omitted provider parameters:** none are documented beyond `platformName` / `address`. No `platform`, `platformId`, `chainId`, `convert`, `aux`, `size`, paging or vendor-selection parameter.
8. **Cache TTL: 300 seconds.** Security records are vendor audit results that change on rescans or contract-state changes (owner/tax/pause changes), far less often than prices (D3/D4 15 s) or holder counts (D16 60 s), but they are not reference data like platforms (D11/D12 900 s): a newly listed token's first scan can appear minutes after listing. 300 s, the existing tier for slowly changing metadata (`cmc_crypto_info`, category routes), bounds that lag to five minutes while absorbing repeated agent calls under the shared keyless IP rate pool. Success-only caching per the existing client (an empty array is a success and is cached); failures never cached. Caching is not a correctness dependency.
9. **Output:** the existing `ProviderEnvelope` passthrough; `data` (the `TokenSecurityResponseDTO[]` array, including an empty array) preserved verbatim. No risk score, verdict, filtering, reordering, de-duplication, coercion (e.g. tax strings to numbers), field renaming, `platformId` translation, or interpretation of `securityLevel`, `isHit`, display statuses or tags. The tool exposes provider data; it does not assert that any token is safe.
10. **Errors and bounds:** the existing stable `ErrorCode` taxonomy (`errors.py`), unchanged, with the existing attempt bounds:
    - validation failure → `INVALID_ARGUMENT`, before any network access;
    - timeout → `UPSTREAM_TIMEOUT`; network error → `UPSTREAM_NETWORK_ERROR` (bounded retries);
    - HTTP 429 after bounded retries → `RATE_LIMITED`;
    - 502/503/504 after bounded retries → `UPSTREAM_5XX`; plain 500 → `UPSTREAM_5XX` on the first attempt;
    - HTTP 400, 403, 404 and other non-429 4xx → `UPSTREAM_HTTP_ERROR`, single attempt;
    - non-success `status.error_code` → `UPSTREAM_APPLICATION_ERROR`;
    - malformed or structurally unexpected 2xx, and any response above the shared **2 MiB** cap (`DEFAULT_MAX_RESPONSE_BYTES`) → `UPSTREAM_CONTRACT_MISMATCH`.
    `UNSUPPORTED_ROUTE` and `INTERNAL_ERROR` are never produced for D8 by classification. An unknown token yields whatever the provider returns under the mapping above; an empty array is success.
11. **Minimum verifier shape (documentation-derived; weakest structural check):** `data` is a **list** (empty allowed) and **every element is a mapping**. Nothing else is required. Rationale:
    - the documented response is an array; a non-list `data` (object, string, `null`) is a genuine contract mismatch;
    - an empty array is a legitimate "no security record" success (see evidence) and must not become `CONTRACT_MISMATCH`, so neither `len > 0` nor `_is_nonempty_list`-style checks are used;
    - no field is required: the DTO marks nothing required and record completeness depends on a third-party vendor, so `platformName`, `platformId`, `tokenContractAddress`, `securityLevel`, `exist`, `extra`, `securityItems`, display objects, taxes and `tags` are not checked, and no echo equality with the requested address is checked (case/checksum of the echo is unobserved; the example shows a lower-case `platformName`).
    A dedicated helper (e.g. `_is_mapping_list`: `isinstance(v, list) and all(isinstance(x, Mapping) for x in v)`) is used in `verify_live.py`. Deterministic live fixture: Ethereum USDC, the D3/D4/D16 identity. Because `LiveProbe` params are provider params (as for D12/D16), the probe is `LiveProbe("cmc_dex_security_detail", {"platformName": "Ethereum", "address": "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48"}, "dex_security_detail")`; the equivalent tool arguments are `{"platform": "Ethereum", "address": "0xA0b8…eB48"}`. If live evidence later shows `data` as a single object rather than an array, record a contract mismatch and amend this record; do not loosen silently.

## Limitations

- Verifier shape is documentation-derived; no live D8 response has been observed. Live D8 verification is pending.
- The empty-array semantics rest on DTO shape, the `exist` field and a CoinMarketCap tutorial, not on a reference-page statement; the weak verifier is chosen so this uncertainty cannot produce a false `CONTRACT_MISMATCH`.
- Whether the provider returns an empty array, an element with `exist: false`, or an application error for an unknown token is unobserved; all three are handled by item 10 without reclassification.
- The method is inferred from the plain cURL example and the keyless GET-only rule; the retrieved rendering of this section shows no explicit method label.
- No required markers were visible for `platformName`/`address`; both are required by this contract, a narrower choice.
- Platform-name semantics are inferred from D4's live evidence (Ethereum only); numeric platform ids, non-EVM addresses and case sensitivity remain unverified.
- Provider security data is third-party vendor output (example `source: "GoPlus"`); it is not a guarantee of token safety and the tool does not present it as one.
- Documentation was read through a fetch service because the sandbox egress blocks `coinmarketcap.com`.
- This record does not accept any implementation and does not satisfy any part of the 32/32 live release gate.
