## Scope

E2-D contains exactly one approved E0 DEX candidate:

- D16 `cmc_dex_holders_count` → `GET /v1/dex/holders/count`

D16 is E0 `SUPPORTED` / `APPROVED` (`V1_1_CAPABILITY_INVENTORY.md`). It is the smallest remaining approved route: two required token-identity inputs and a small single-object response. D6 (list/size semantics), D8 (rich security array), D1/D2/D7/D9/D10/D13/D14 (search, pagination, pair or interval contracts), holder list/detail and every other route are outside E2-D. D5 remains deferred; D15 and D17 remain excluded (`EXCLUDED_NON_GET`). The holder trend-list and tag-count routes on the same documentation page are GET query routes but carry no keyless note and are not in the frozen inventory; they are excluded for that reason, not because of their HTTP method. Frozen N = 32 is unchanged. E2-A, E2-B and E2-C are not reopened.

## Evidence

### Current official documentation (retrieved 2026-10-02)

Direct access to `coinmarketcap.com` is blocked by this sandbox's egress proxy; the pages were retrieved through a read-only web-fetch service and are summarised here, not copied.

1. **Holder category reference** — <https://coinmarketcap.com/api/documentation/pro-api-reference/holder>, section "Get holder count":
   - `GET /v1/dex/holders/count` (the cURL example is a plain GET with a query string; no request body);
   - "Available with no API key … Prefix the path with `/public-api`: `https://pro-api.coinmarketcap.com/public-api/v1/dex/holders/count`";
   - query parameters: exactly `platform` and `tokenAddress`, no others; both are required by this contract; the retrieved documentation rendering shows no required markers or descriptions for this section ( the sibling holder sections describe `platform` as "Blockchain platform" / "Platform name or id" and `tokenAddress` as "Token contract address");
   - response 200 `HolderCountVO`, a single object with exactly three documented fields: `platformId` (integer, int32), `count` (integer, int64), `tokenAddress` (string). Example: `{"platformId": 0, "count": 0, "tokenAddress": "tokenAddress"}`. No field is marked required. The documented example is the bare `HolderCountVO`; that it arrives as `data` inside the standard `{status, data}` envelope follows from the keyless page's "same JSON envelope" statement, not from a D16-specific example.
   - D15 (`/v1/dex/holders/list`) and D17 (`/v1/dex/holders/detail`) on the same page are documented as POST with JSON bodies, consistent with their E0 exclusion.
2. **Keyless Public API reference** — <https://coinmarketcap.com/api/documentation/pro-api-reference/keyless-public-api>: "18 Standard API and 17 DEX endpoints, keyless"; "Keyless endpoints accept `GET` only"; no `X-CMC_PRO_API_KEY` needed; same JSON envelope as the keyed API. The page lists holders among the keyless DEX data families.

### Reconciliation with accepted E2-A/B token identity

E2-A (live, credential-free, 2026-10-02) established that the `platform` + `address` pair on `/v1/dex/token/price` accepts platform *names* (`Ethereum` and `ethereum` both succeeded for Ethereum USDC) and accepted the bounded, case-preserving `DexPlatform` / `DexAddress` types; E2-B reused them unchanged for D3. D16 documents the same two identities: the provider key `platform` is identical, and the token contract address is named `tokenAddress` instead of `address`. Nothing in the documentation indicates a different value domain, so:

- the public interface reuses `platform` + `address`, and only the provider wire key differs (`address` → `tokenAddress`), exactly as E2-C maps `platform` → `platformName`;
- sibling sections say "Platform name or id"; numeric platform ids are **not** exposed (`DexPlatform` accepts digit strings, but numeric-id semantics are unverified and are not documented as a contract).

The D16 verifier shape is therefore **documentation-derived**, and live D16 verification is **pending** (32/32 release qualification via `live-release-qualification.yml`). The E0 `SUPPORTED` classification is unchanged and not re-asserted here.

No evidence conflicts with E0.

## Contract: `cmc_dex_holders_count`

1. **Tool name:** `cmc_dex_holders_count`.
   **Description (frozen wording):** "Get the CoinMarketCap DEX holder count for one token identified by platform name and token contract address; use platform-list to discover platform names." House style (leading capital, terminal period), as for the other descriptions.
2. **Route:** `GET /v1/dex/holders/count` on the fixed keyless base `https://pro-api.coinmarketcap.com/public-api`; one tool ↔ one allowlisted route; no credentials, auth headers, request body or authenticated fallback.
3. **Input schema:** strict object, `additionalProperties: false`, required `platform` and `address`, no optional fields, no defaults.
4. **Public argument names:** `platform` + `address`, consistent with D3/D4. No `token_address` / `tokenAddress` public argument is introduced; the provider spelling is a wire detail.
5. **Types:** E2-A's `DexPlatform` (1–64 chars; no control characters, `&`, `=`, `?`, `#`, or leading/trailing whitespace; case preserved; no local enum) and `DexAddress` (`^[A-Za-z0-9_.:-]{1,128}$`; case preserved; no EVM `0x`/length rule) reused **unchanged**. The JSON-schema fragments for both properties must be identical to `cmc_dex_token`'s and `cmc_dex_token_price`'s.
6. **Query serialization:** exactly `{"platform": <platform>, "tokenAddress": <address>}` — those provider keys, that order, values passed through unchanged (no case folding, trimming, checksum normalization, or platform-name→id mapping). Built by a new top-level pure helper `models.dex_holders_count_params(platform, address)` so the key construction is visible to mutmut; the handler only delegates to it. Reusing `dex_token_params` / `dex_token_price_params` is not allowed (wrong provider key, and it would couple route wire contracts).
7. **Omitted provider parameters:** none are documented beyond `platform` / `tokenAddress`. No `tag`, `convert`, `aux`, paging, size or interval parameter, and no numeric platform-id parameter.
8. **Cache TTL: 60 seconds.** Holder count is on-chain state that changes with transfers, but far more slowly and less consequentially than D3/D4 prices (15 s); it is not reference data like D11/D12 (900 s). 60 s bounds staleness to one short window while absorbing repeated agent calls under the shared keyless IP rate pool. Success-only caching per the existing client; failures never cached. Caching is not a correctness dependency.
9. **Output:** the existing `ProviderEnvelope` passthrough; `data` (the `HolderCountVO` object) preserved verbatim; no renaming, coercion, filtering, or derived values; `platformId` is not translated to a platform name.
10. **Errors and bounds:** the existing stable `ErrorCode` taxonomy (`errors.py`), unchanged, with the existing attempt bounds:
    - validation failure → `INVALID_ARGUMENT`, before any network access;
    - timeout → `UPSTREAM_TIMEOUT`; network error → `UPSTREAM_NETWORK_ERROR` (bounded retries);
    - HTTP 429 after bounded retries → `RATE_LIMITED`;
    - 502/503/504 after bounded retries → `UPSTREAM_5XX`; plain 500 → `UPSTREAM_5XX` on the first attempt;
    - HTTP 400, 404 and other non-429 4xx → `UPSTREAM_HTTP_ERROR`, single attempt;
    - non-success `status.error_code` → `UPSTREAM_APPLICATION_ERROR`;
    - malformed or structurally unexpected 2xx, and any response above the shared **2 MiB** cap (`DEFAULT_MAX_RESPONSE_BYTES`, `client._raise_oversized`) → `UPSTREAM_CONTRACT_MISMATCH`.
    `UNSUPPORTED_ROUTE` and `INTERNAL_ERROR` are never produced for D16 by classification. An unknown token yields whatever the provider returns under the mapping above.
11. **Minimum verifier shape (documentation-derived):** `data` is a mapping whose `count` is a **non-negative non-bool integer** (zero is valid). Rationale:
    - `count` is the one field the route exists to return and is documented as int64.
    - `count > 0` is not required: zero holders is a legitimate value, and `_is_positive_int` must not be reused.
    - `tokenAddress` is **not** required: the DTO marks nothing required, and presence/case of the echo is unobserved; equality with the requested address is not checked.
    - `platformId` is not required; its value domain is undocumented beyond int32.
    A dedicated helper (e.g. `_is_nonnegative_int`: `isinstance(v, int) and not isinstance(v, bool) and v >= 0`) is used. Deterministic live fixture: Ethereum USDC, the D3/D4 identity. Because `LiveProbe` params are provider params (as for D12), the probe is `LiveProbe("cmc_dex_holders_count", {"platform": "Ethereum", "tokenAddress": "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48"}, "dex_holders_count")`; the equivalent tool arguments are `{"platform": "Ethereum", "address": "0xA0b8…eB48"}`. If live evidence later shows `count` absent, negative, or non-integer (e.g. a string), record a contract mismatch and amend this record; do not loosen silently.

## Required non-live tests

- Existing 22 tools unchanged: names, descriptions, schemas, routes, TTLs.
- `cmc_dex_holders_count` name, frozen description, route, 60 s TTL pinned; total tool count 23; `/v1/dex/holders/count` in the route allowlist exactly once.
- Schema snapshot: strict, required `platform`/`address`, no other properties; property fragments equal to `cmc_dex_token`'s.
- Validation before network (zero upstream calls): missing either field; unknown field (including `tokenAddress`, `token_address`, `tag`); empty; overlong (65-char platform, 129-char address); leading/trailing whitespace; control characters; `&`, `=`, `?`, `#` in platform; `/`, space, `%`, `&` in address; non-string types (including integer platform id).
- Boundary acceptance: 64-char platform, 128-char address, non-ASCII platform with inner spaces (`B² Network`), mixed-case address.
- `dex_holders_count_params`: exact keys `platform`, `tokenAddress`, that order, value identity, no `address` key, no extra keys; handler delegates to it; wire-level query-string test (case preservation, percent-encoding of inner spaces, `tokenAddress=` present and `address=` absent).
- Request is GET to `https://pro-api.coinmarketcap.com/public-api/v1/dex/holders/count`, no body, no auth/API-key header.
- `ProviderEnvelope` passthrough of a `HolderCountVO` fixture (including `count: 0` and a large int64 count) byte-identical after JSON round-trip.
- Error mapping with exact codes and attempt counts as in item 10 (timeout, network, 429, 502/503/504, 500, 400, 404, application error, malformed, non-JSON, over 2 MiB).
- Caching: hit within 60 s; miss after expiry; failures not cached; case-distinct `(platform, address)` keys not conflated; D16 and D3/D4 caches independent for the same identity.
- Verifier: accepts `count` 0 and positive; rejects non-mapping, missing `count`, negative, bool, float, string `"5"`, `None`; does not require `tokenAddress` or `platformId`; exactly one D16 probe with the provider params above.
- D5, D6, D8, D15, D17, holder trend/tag-count and every other unapproved DEX route absent.

## Limitations

- Verifier shape is documentation-derived; no live D16 response has been observed. Live D16 verification is pending.
- No required markers were visible for `platform`/`tokenAddress` in the retrieved rendering; both are required by this contract, a narrower choice that does not depend on the markers.
- Platform-name semantics are inferred from D4's live evidence (Ethereum only); numeric platform ids, non-EVM addresses and case sensitivity remain unverified.
- Whether `count` is serialized as a JSON integer (documented) rather than a string is unobserved; the verifier would flag a string as a mismatch.
- Documentation was read through a fetch service because the sandbox egress blocks `coinmarketcap.com`.
- This record does not accept any implementation and does not satisfy any part of the 32/32 live release gate.
