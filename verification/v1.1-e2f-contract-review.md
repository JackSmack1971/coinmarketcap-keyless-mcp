## Scope

E2-F contains exactly one approved E0 DEX candidate:

- D6 `cmc_dex_token_pools` → `GET /v1/dex/token/pools`

D6 is E0 `SUPPORTED` / `APPROVED` (`V1_1_CAPABILITY_INVENTORY.md`). It is the smallest remaining approved route: its current documentation exposes only `platform`, `address` and `size`. D7 exposes five search parameters; D9/D10, D13/D14 and the pair/K-line routes have materially larger filtering, pagination or interval contracts. D1, D2, D7, D9, D10, D13, D14 and every other route are outside E2-F. D5 remains deferred; D15 and D17 remain excluded (`EXCLUDED_NON_GET`). Frozen N = 32 is unchanged. E2-A through E2-E are not reopened; D8's acceptance authorizes nothing here.

## Evidence

### Current official documentation (retrieved 2026-10-02)

The sandbox's egress proxy blocks direct access to `coinmarketcap.com`, so the pages were retrieved through a read-only web-fetch service. They are summarised here, not copied.

1. **Token category reference**: <https://coinmarketcap.com/api/documentation/pro-api-reference/token>, section "Get token pools" (listed as `/v1/dex/token/pools - Get Token Pools`):
   - "Get all pools for a specific token";
   - "Available with no API key … Prefix the path with `/public-api`: `https://pro-api.coinmarketcap.com/public-api/v1/dex/token/pools`";
   - the cURL example is a plain request with no `--request`, no body and no content type. The POST siblings on the same page (trending, batch price, new, meme, gainer-loser) all use `--request POST` with a body. Together with the keyless GET-only rule, this fixes the method as GET;
   - query parameters: exactly `platform` ("Platform name"), `address` ("Token address") and `size` (`integer · int32`, "Default: 20"). No description, minimum, maximum or required marker is rendered for `size`. No required markers are visible for any parameter;
   - response 200, rendered as a **JSON array** of pool objects (`[ { … } ]`). The rendered structure is identical to D3 `pls`, and this record calls it `TokenTopPoolDTO`; the retrieved rendering does not print the DTO name. Documented fields:
     - `addr` (pool address);
     - `v24` ("24-hour trading volume", string in the example);
     - `pubAt` ("Publish timestamp", integer);
     - `t0` / `t1` ("Basic token info in the pool": `addr`, `lg`, `n`, `sym`, `liq`, `liqUsd`);
     - `bidx` ("Index of the base token in the pool (0 or 1)");
     - `exid`, `exn` (exchange identifier and name; the rendered labels are partially misaligned: "Exchange name" is attached to `exid`);
     - `liqUsd` ("Liquidity in USD", string);
     - `fa` ("Factory address");
     - `lr` ("Locked rate"), `br` ("Burned rate");
     - `top` ("Is top pool"), `mi` ("Is meme inner pool").

     No field is marked required.
   - The same `TokenTopPoolDTO` shape appears embedded as `pls` in D3 `TokenDetailDTO` (`/v1/dex/token`), next to `nps` ("Number of top pools"). D6 is therefore the standalone list of the same pool records that D3 already returns inline.
2. **Keyless Public API reference**: <https://coinmarketcap.com/api/documentation/pro-api-reference/keyless-public-api>, as accepted in E2-A to E2-E. It lists `/v1/dex/token/pools` among the keyless DEX endpoints. Keyless endpoints accept `GET` only and return the same `{status, data}` envelope as the keyed Pro API. The array arriving as `data` follows from this statement, not from a D6-specific envelope example.

### `size` evidence

The only authoritative statements are the type (`int32`) and the default (`20`). No accepted minimum or maximum, error behaviour for out-of-range values, or clamping is documented. The page does not say whether `size=0` or a negative value is accepted, rejected, clamped or treated as "all". No live evidence exists. Repository convention (for example `limit` bounds on Standard routes) is not evidence for this provider route.

### Evidence on empty results

No reference page states what D6 returns for a token with no pools. The response is an array, so zero elements is structurally expressible. "Get all pools" plus a default `size` of 20 implies a variable-length list. D3 models the pool count separately (`nps`), which also implies the count can vary and may be zero (for example a token that is not traded on a tracked DEX). Conclusion: an empty `data` array is a legitimate success, not `UPSTREAM_CONTRACT_MISMATCH`.

### Reconciliation with accepted E2-A/B identity

D6 documents `platform` ("Platform name") and `address` ("Token address"), the same provider keys, descriptions and value domain as D4 (E2-A, live-observed name semantics for Ethereum USDC) and D3 (E2-B). Public and wire names coincide, as for D3/D4. Numeric platform ids are not exposed, and their semantics are not part of the contract.

### Live evidence

**None collected for E2-F.** Documentation plus E2-A/B evidence resolves every decision below. The open questions (`size` bounds, empty array) are resolved by narrower contract choices rather than by probing, and this sandbox cannot reach `pro-api.coinmarketcap.com`. The D6 verifier shape is **documentation-derived**, and live D6 verification is **pending** (32/32 release qualification via `live-release-qualification.yml`). The E0 `SUPPORTED` classification is unchanged and not re-asserted here.

No evidence conflicts with E0.

## Contract: `cmc_dex_token_pools`

1. **Tool name:** `cmc_dex_token_pools`.
   **Description (frozen wording):** "Get CoinMarketCap DEX liquidity pools for one token identified by platform name and token contract address, using the provider's default result size; returns provider pool records as-is; use platform-list to discover platform names." House style (leading capital, terminal period).
2. **Route:** `GET /v1/dex/token/pools` on the fixed keyless base `https://pro-api.coinmarketcap.com/public-api`. One tool maps to one allowlisted route. No credentials, auth headers, request body or authenticated fallback.
3. **Input schema:** strict object, `additionalProperties: false`, required `platform` and `address`, no optional fields, no defaults. `size` is **not** a property (item 5).
4. **Types:** E2-A's `DexPlatform` (1–64 chars; no control characters, `&`, `=`, `?`, `#`, or leading/trailing whitespace; case preserved; no local enum) and `DexAddress` (`^[A-Za-z0-9_.:-]{1,128}$`; case preserved; no EVM `0x`/length rule) are reused **unchanged**. The JSON-schema fragments for both properties must be identical to `cmc_dex_token`'s.
5. **`size` semantics: deliberately not exposed.**
   - **Exposed?** No. A public `size` would need validated bounds. The documentation gives none, and manufacturing a range (for example 1–100) from convention would publish a contract the provider has not stated. The narrower choice is to omit it.
   - **Optional vs required:** not applicable. A `size` argument is an unknown argument and is rejected with `INVALID_ARGUMENT` before network access.
   - **Default behaviour:** the provider's documented default (`20`) applies. The tool does not assert that exactly 20, at most 20, or any particular count is returned.
   - **Serialization:** `size` is **omitted** from the wire query. It is not serialized as `20`, so the request relies on the provider default rather than restating it. If the provider default changes, the tool follows it, and the response stays bounded by the shared 2 MiB cap.
   - **Bounded-input invariant:** satisfied, because no list-size input exists. Response size is bounded by the provider default and the 2 MiB cap.
   - **Future exposure:** adding `size` later requires authoritative bounds (documentation or recorded live evidence) and a contract amendment. It is an additive public-contract change.
6. **Query serialization:** exactly `{"platform": <platform>, "address": <address>}`: those provider keys, that order, values passed through unchanged (no case folding, trimming, checksum normalization or name→id mapping), and no `size` key. It is built by a new top-level pure helper `models.dex_token_pools_params(platform, address)`, so the key construction is visible to mutmut; the handler only delegates to it. Reusing `dex_token_params`, `dex_token_price_params` or any other helper is not allowed. The keys currently coincide, but sharing a helper would couple independent route wire contracts, and a later `size` amendment must not touch D3/D4.
7. **Omitted provider parameters:** `size` (item 5). No other parameter is documented. No `platformName`, `tokenAddress`, `platformId`, `chainId`, `convert`, `aux`, sort, page/cursor, interval or exchange filter.
8. **Cache TTL: 15 seconds.** Every element carries fast-moving market values (`v24`, `liqUsd`, `t0.liqUsd`/`t1.liqUsd`, `liq`). These are the same `TokenTopPoolDTO` fields D3 `cmc_dex_token` already returns inline as `pls`, which the accepted E2-B contract caches for 15 s, and D4 price is also 15 s. A longer TTL (D16 60 s, D8 300 s) would serve pool liquidity/volume staler than the identical fields from D3, an inconsistency with no justification. Pool membership changes slowly, but the record values do not, and the TTL is set by the most dynamic content. 15 s still absorbs bursts of repeated agent calls under the shared keyless IP rate pool. The existing client caches successes only: an empty array is a success and is cached, and failures are never cached. Caching is not a correctness dependency.
9. **Output:** the existing `ProviderEnvelope` passthrough. `data` (the `TokenTopPoolDTO[]` array, including an empty array) is preserved verbatim. No re-sorting, filtering (for example by `top` or `mi`), truncation, de-duplication, string→number coercion of `v24`/`liqUsd`/`lr`/`br`, field renaming, exchange-id translation, aggregation (total liquidity) or derived metrics.
10. **Errors and bounds:** the existing stable `ErrorCode` taxonomy (`errors.py`), unchanged, with the existing attempt bounds:
    - validation failure (including an unknown `size` argument) → `INVALID_ARGUMENT`, before any network access;
    - timeout → `UPSTREAM_TIMEOUT`; network error → `UPSTREAM_NETWORK_ERROR` (bounded retries);
    - HTTP 429 after bounded retries → `RATE_LIMITED`;
    - 502/503/504 after bounded retries → `UPSTREAM_5XX`; a plain 500 → `UPSTREAM_5XX` on the first attempt;
    - HTTP 400, 403, 404 and other non-429 4xx → `UPSTREAM_HTTP_ERROR`, single attempt;
    - non-success `status.error_code` → `UPSTREAM_APPLICATION_ERROR`;
    - malformed or structurally unexpected 2xx, and any response above the shared **2 MiB** cap (`DEFAULT_MAX_RESPONSE_BYTES`) → `UPSTREAM_CONTRACT_MISMATCH`.

    `UNSUPPORTED_ROUTE` and `INTERNAL_ERROR` are never produced for D6 by classification. An unknown token yields whatever the provider returns under this mapping. An empty array is success.
11. **Minimum verifier shape (documentation-derived; the weakest structural check):** `data` is a **list** (empty allowed) and **every element is a mapping**. Nothing else is required. Rationale:
    - the documented response is an array, so a non-list `data` (object, string, `null`) is a genuine contract mismatch;
    - an empty array is a legitimate "no pools" success (see evidence) and must not become `CONTRACT_MISMATCH`, so no `len > 0` check is made. This holds even for the Ethereum USDC fixture: the verifier asserts structure, not market state;
    - no field is required. The DTO marks nothing required, and the dynamic fields (`v24`, `liqUsd`, `lr`, `br`, `t0`/`t1` and their nested fields, `exid`/`exn`, `top`, `mi`) depend on market state and exchange metadata. `addr` is not required either, and nothing is compared with the request (no echo check of the token in `t0`/`t1`);
    - no element count is checked against the default 20 (item 5).

    The existing `_is_mapping_list` helper in `verify_live.py` (added by E2-E) is reused unchanged, under a new check key `dex_token_pools`. The probe carries a comment in the E2-B/E2-E style: tool arguments platform/address (the D3/D4 identity), sent unchanged as provider keys platform and address, as `models.dex_token_pools_params` does; size omitted. Deterministic live fixture: Ethereum USDC, the D3/D4/D8/D16 identity. The provider params coincide with the tool arguments: `LiveProbe("cmc_dex_token_pools", {"platform": "Ethereum", "address": "0xA0b86991c6218b36c1d19D4a2e9Eb0cE3606eB48"}, "dex_token_pools")`, with no `size`. If live evidence later shows `data` as a non-array, record a contract mismatch and amend this record. Do not loosen the check silently.

## Required non-live tests

- The existing 24 tools are unchanged: names, descriptions, schemas, routes and TTLs, in the same order.
- `cmc_dex_token_pools` name, frozen description, route and 15 s TTL are pinned. Total tool count is 25, and `/v1/dex/token/pools` appears in the route allowlist exactly once.
- Schema snapshot: strict, required `platform`/`address`, no other properties (in particular no `size`). The property fragments equal `cmc_dex_token`'s.
- Validation happens before network access (zero upstream calls) for:
  - a missing field;
  - unknown fields: `size` (int 20, int 1, string `"20"`, `null`), `limit`, `platformName`, `tokenAddress`;
  - empty values;
  - overlong values (65-char platform, 129-char address);
  - leading/trailing whitespace;
  - control characters;
  - `&`, `=`, `?`, `#` in platform;
  - `/`, space, `%`, `&` in address;
  - non-string types (including an integer platform id).
- Boundary acceptance: 64-char platform, 128-char address, a non-ASCII platform with inner spaces (`B² Network`), a mixed-case address.
- `dex_token_pools_params`:
  - exact keys `platform` then `address`, with value identity;
  - no `size` key and no extra keys;
  - the handler delegates to it;
  - a wire-level query-string test: case preserved, inner spaces percent-encoded, `size=` absent.
- The request is a GET to `https://pro-api.coinmarketcap.com/public-api/v1/dex/token/pools`, with no body and no auth/API-key header.
- `ProviderEnvelope` passthrough is byte-identical after a JSON round trip for:
  - the documented full record;
  - an empty array;
  - a sparse `{}` element;
  - string `v24`/`liqUsd`/`lr`/`br` (not coerced);
  - a multi-element array with order preserved;
  - more than 20 elements (no truncation).
- A 200 response whose `data` is a single object passes through the tool unchanged. Only the live verifier flags that shape.
- Error mapping with exact codes and attempt counts as in item 10: timeout, network, 429, 502/503/504, 500, 400, 403, 404, application error, malformed, non-JSON and over 2 MiB.
- Caching:
  - a hit within 15 s and a miss after expiry;
  - an empty-array success is cached;
  - failures are not cached;
  - case-distinct `(platform, address)` keys are not conflated;
  - the D6 cache is independent of the D3/D4/D8/D16 caches for the same identity.
- Verifier:
  - accepts `[]`, one full record and a sparse `{}` element;
  - rejects a bare object, `None`, a string, and a list with a non-mapping (`[1]`, `[None]`, `[[]]`);
  - requires no field;
  - has exactly one D6 probe, whose check key is exactly `dex_token_pools`, with provider params `platform`/`address` and no `size`. Pinning the check key is required to kill V7, because `dex_security_detail` uses the same predicate.
- D1, D2, D5, D7, D9, D10, D13, D14, D15, D17 and every other unapproved route are absent.

## Limitations

- The verifier shape is documentation-derived. No live D6 response has been observed, and live D6 verification is pending.
- `size` bounds are undocumented, so `size` is not exposed. Callers get only the provider default number of pools. That this default is 20, or that it caps the result, rests on documentation only.
- The empty-array semantics rest on the array shape, "get all pools" and D3's separate `nps` count, not on a reference-page statement. The weak verifier is chosen so that this uncertainty cannot produce a false `CONTRACT_MISMATCH`.
- Whether an unknown token returns an empty array, an application error or an HTTP error is unobserved. All three are handled by item 10 without reclassification.
- The method is inferred from the plain cURL example and the keyless GET-only rule. The retrieved rendering shows no explicit method label for this section.
- No required markers were visible. Both `platform` and `address` are required by this contract, which is the narrower choice.
- Platform-name semantics are inferred from D4's live evidence (Ethereum only). Numeric platform ids, non-EVM addresses and case sensitivity remain unverified.
- Documentation was read through a fetch service because the sandbox egress blocks `coinmarketcap.com`.
- This record does not accept any implementation and does not satisfy any part of the 32/32 live release gate.

## Independent review

**Review date:** 2026-10-02. The reviewer was a fresh-context agent with no drafting context. It edited nothing and made no live CoinMarketCap calls.

**Disposition: APPROVE WITH NOTES (no blockers).** The reviewer independently re-fetched the token reference page (through the same read-only fetch service) and confirmed the "Get token pools" section:
- the keyless `/public-api/v1/dex/token/pools` path;

- `models.py` is inside `only_mutate` and `verify_live.py` is outside it, so no configuration change is needed;
- item 10 matches `client.py`: the retry set is `{429, 502, 503, 504}`, non-429 4xx is single-attempt, a plain 500 is `UPSTREAM_5XX` on the first attempt, and an over-2 MiB response is `UPSTREAM_CONTRACT_MISMATCH`;
